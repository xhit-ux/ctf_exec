# 角色划分任务文档

**文档更新时间**: 2026-03-17  
**关联文件**: `db/final_01.sql`, `progress/progress_01.md`

---

## 1. 目标与范围

本任务用于落地平台权限分层，确保管理员能力可控、可审计、可扩展。

角色模型：
1. `root`：仅负责高危管理能力（用户角色变更）
2. `admin`：赛事与题目管理能力
3. `user`：参赛、提交、团队、个人资料能力

认证来源模型：
1. `auth_provider` 表示登录来源（`local/github/...`）
2. 不参与授权判断

---

## 2. 数据库改造（已纳入 `final_01.sql`）

1. `users.role` 增加约束：只允许 `root/admin/user`
2. 增加 `users.role` 索引，优化后台筛选与权限查询
3. 初始化脚本补齐 `DROP TABLE IF EXISTS contest_scores`
4. 默认创建 `root` 用户（用于首个高权限初始化）
5. 审计最小方案：通过 `user_activity_logs` 记录 `action_type='role_change'`

`details` 字段建议 JSON 结构：

```json
{
  "operator_id": "<root_user_id>",
  "old_role": "user",
  "new_role": "admin",
  "reason": "promote for contest ops"
}
```

---

## 3. 后端任务拆解

### 3.1 RBAC 基线

1. 定义角色常量：`RoleRoot/RoleAdmin/RoleUser`
2. 实现角色校验函数：`IsValidRole(role string)`
3. 增加统一中间件：`RequireRoles("root")`、`RequireRoles("root", "admin")`

### 3.2 root 专用能力

1. API：`PATCH /api/admin/users/:id/role`
2. 仅允许 `root` 调用
3. 写入角色变更审计日志
4. 规则：禁止非法角色值；建议禁止 root 自降级

### 3.3 admin 业务能力

1. 题目 CRUD 路由挂载到 `RequireRoles("root", "admin")`
2. 赛事 CRUD 与赛事编排路由挂载到 `RequireRoles("root", "admin")`

### 3.4 Token 一致性

1. 评估使用短 TTL + 角色变更后强制重新登录
2. 采用 Redis 黑名单或 token version 机制

---

## 4. 验收标准

1. 非 `root` 无法修改任何用户角色
2. `admin` 可管理赛事与题目，但不能修改用户角色
3. `user` 无法访问管理端写接口
4. 每次角色变更均产生 `role_change` 审计记录
5. 初始化数据库后默认存在可登录的 `root` 账号

---

## 5. 执行顺序建议

1. 先改数据库约束与初始化脚本
2. 再做后端 RBAC 中间件和 root 角色管理 API
3. 最后把赛事/题目管理路由切到统一 RBAC

该顺序可保证改造过程可回滚、影响面可控。
